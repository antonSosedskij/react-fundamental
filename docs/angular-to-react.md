# Angular → React

Заметки по этапам: как это сделали бы в Angular и почему в React иначе.

## Стартовые соответствия

| Angular                              | React                                        | Главное отличие                                                   |
| ------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------- |
| Компонент с шаблоном                 | Функция, возвращающая JSX                    | Функция вызывается заново при каждом рендере                      |
| `@Input()` / `input()`               | props                                        | Только чтение, без сеттеров                                       |
| `@Output()` / `output()`             | callback в props (`onSkip`)                  | Просто функция                                                    |
| `signal()`                           | `useState`                                   | Новое значение → ререндер всего компонента                        |
| `computed()`                         | Обычная переменная в теле компонента         | Пересчитывается на каждом рендере; `useMemo` — только если дорого |
| `effect()`                           | `useEffect`                                  | Явный массив зависимостей и cleanup                               |
| `ngOnDestroy` / `takeUntilDestroyed` | Функция, возвращаемая из `useEffect`         | Срабатывает и перед каждым перезапуском эффекта                   |
| Сервис + DI                          | Context + хук                                | Нет иерархии инжекторов — только дерево провайдеров               |
| NgRx store/reducer                   | `useReducer`                                 | Локально в компоненте; глобально — через Context                  |
| `@ViewChild`                         | `useRef`                                     | Ref ещё и «переменная экземпляра», не вызывающая ререндер         |
| Reactive Forms                       | Контролируемые инпуты (`value` + `onChange`) | Стейт формы — обычный стейт                                       |
| Change detection (Zone / сигналы)    | Ререндер поддерева при смене стейта          | Ререндер ≠ изменение DOM                                          |

## Этап 2

### Редьюсер = сервис, разобранный на части

| Angular-сервис              | React `useReducer`                              |
| --------------------------- | ----------------------------------------------- |
| `signal` с состоянием       | `state` — хранит React, не компонент            |
| методы `start()`, `pause()` | обработчики в редьюсере (`timerActionHandlers`) |
| вызов `service.start()`     | `dispatch({ type: 'START', now: Date.now() })`  |

- Компонент не знает правил, только сообщает «что случилось». Правила — в редьюсере, тестируются без React.
- Редьюсер чистый: `Date.now()`, рандом, запросы — в обработчике клика, в редьюсер приходят готовым значением в экшене. React может вызвать редьюсер дважды (StrictMode).
- Иммутабельность: новый объект через spread. Вернул тот же объект (`return state`) → React сравнил по ссылке и не перерисовал.
- Lazy init: `useReducer(reducer, DEFAULT_SETTINGS, createInitialTimerState)` — третий аргумент вызывается один раз на маунте.
- Состояние ничего не рисует само: UI видит только то, что из state прочитали и передали в пропсы (баг с захардкоженным `status="idle"`).
- Нейминг: `onX` — имя пропа, `handleX` — функция, которую в него передаёшь.

### State — снимок рендера

- `const { status, mode } = state` — нормально, значения свежие. Функция компонента перевыполняется целиком на каждом рендере, `useReducer` каждый раз отдаёт текущий state, деструктуризация создаёт новые константы.
- В Angular аналог сломался бы: `this.status = store.status` в конструкторе копируется один раз и застывает — там долгоживущий экземпляр, а шаблон читает его поля. В React экземпляра нет, тело функции и есть шаблон.
- Хуки работают не на замыканиях: React хранит state снаружи и привязывает к компоненту по порядку вызова хуков (поэтому хуки нельзя в `if`).
- Замыкания — с другой стороны: функция, созданная в рендере, видит значения этого рендера. После `dispatch` в том же обработчике `state` ещё старый, новый придёт в следующем рендере. Колбэк `setTimeout`/`setInterval` из старого рендера видит старый state (stale closure — этап 3).
- Почитать: https://react.dev/learn/state-as-a-snapshot

### Рендер vs обновление DOM

- **Angular:** `tick()` обходит дерево и сам ищет изменения в биндингах (dirty checking), патчит DOM. Класс компонента не перевыполняется — только функция обновления шаблона.
- **React:** изменение сообщают явно, React перевызывает функцию компонента и сравнивает результат.
- Три фазы:
  1. **Trigger** — кто-то попросил рендер.
  2. **Render** — вызвать функции компонентов, получить новое дерево React-элементов (обычные JS-объекты `{ type, props }`). DOM не тронут.
  3. **Commit** — сравнить новое дерево с предыдущим (reconciliation, `key`) и применить к DOM только разницу.
- Рендер ≠ обновление DOM: рендер — это вызов функции, который выдаёт описание UI. Если описание совпало с прошлым, в DOM ничего не пишется. Пример: при старте таймера перерендерится `ModeSwitcher`, но его кнопки те же — DOM не меняется.
- Поэтому рендер дешёвый и его не надо бояться. `memo` — только когда сам вызов функции дорогой.
- Что запускает ререндер:
  - `setState`/`dispatch` с новым значением (по `Object.is`; то же значение → bail-out). Несколько в одном обработчике — один рендер (batching).
  - Ререндер родителя → рендерятся все дети, даже если пропсы те же. «Изменились пропсы» — не отдельный триггер.
  - Context и внешние сторы — позже.
- Что не запускает: мутация объекта, обычная переменная, `ref`.
- По гранулярности React ближе к Angular с `OnPush`, чем к сигналам: единица обновления — компонент целиком, а не биндинг.
- Почитать: https://react.dev/learn/render-and-commit

## Этап 3

### `useEffect` vs `effect()` / хуки жизненного цикла

- Эффект — синхронизация с внешним миром (интервал, время, подписки, DOM API), а не «хук жизненного цикла». Думать «start → stop», а не «маунт → анмаунт».
- Срабатывает после коммита, то есть только для UI, который реально попал на экран.
- Cleanup (функция, которую возвращает эффект) — не `ngOnDestroy`: вызывается и при уходе компонента, и перед каждым перезапуском эффекта.
- Если эффект ничего не создаёт и не подписывается — cleanup не нужен. Можно вернуть cleanup только из ветки `if`.
- StrictMode в dev монтирует → размонтирует → монтирует снова, чтобы проверить cleanup. Действие в эффекте должно быть идемпотентным: `COMPLETE` из не-`running` возвращает тот же state, поэтому двойной вызов безопасен.
- Почитать: https://react.dev/learn/synchronizing-with-effects

### Зависимости

- `effect()` в Angular трекает прочитанные сигналы сам. В `useEffect` прочитанное перечисляешь руками, `exhaustive-deps` проверяет статически.
- Зависимости — не «на что реагировать», а всё, что эффект читает из тела компонента. React сравнивает каждую через `Object.is`: изменилась хоть одна → cleanup + перезапуск.
- Забыл зависимость (`[]` при чтении `intervalMs`) → эффект навсегда держит значение первого рендера (stale closure).
- Деструктуризация внутри эффекта (`const { endsAt } = state`) делает зависимостью весь `state`. Деструктурировать снаружи, в массив — примитивы.
- `dispatch` и `setState` стабильны (одна функция на все рендеры) — линтер их не требует. Если пришли пропом — линтер не знает, класть.
- Колбэк, переданный в интервал, видит state рендера, в котором интервал создан. Поэтому `COMPLETE` не в колбэке `useNow`, а в эффекте `TimerPanel`, который смотрит на свежий остаток.

### Чистота рендера

- React может вызвать рендер вхолостую: StrictMode (дважды), прерванный concurrent-рендер, рендер без коммита. Рендер — вычисление, не действие.
- Нельзя в рендере: `Date.now()`, рандом, `dispatch`, запросы. Клик → обработчик, синхронизация → эффект.
- Аналог из Angular: выражения в шаблоне без побочных эффектов, иначе `ExpressionChangedAfterItHasBeenCheckedError` (тоже двойная проверка в dev). В React чистым должно быть всё тело компонента — оно и есть шаблон.
- Почитать: https://react.dev/learn/keeping-components-pure

### Вычисляемое — при рендере, а не в state

- Остаток и строка времени — обычные `const` из `state` и `now`. Хранить их в state = дублировать и рисковать рассинхроном. Аналог `computed()` без обёртки.
- Синхронный `setState` в теле эффекта (`react-hooks/set-state-in-effect`) — эффект опаздывает: неправильный кадр уже нарисован, потом второй рендер. Сначала ищи, как получить значение при рендере.
- Кейс: после старта первый кадр показывал `32:06` из-за старого `now`. Починили не в хуке, а в селекторе: `min(remainingMs, endsAt - now)` — старый `now` стал безвредным.
- Кастомный хук (`useNow`) — не сервис: у каждого вызвавшего компонента свой state, общего экземпляра нет.
- Почитать: https://react.dev/learn/you-might-not-need-an-effect

## Этап 4

### Производные значения без `useMemo`

- Прогресс, номер помодоро, строка времени — обычные `const` из `state` и `now` в теле компонента. Пересчитываются на каждом рендере, и это нормально.
- `computed()` в Angular мемоизирует всегда. В React по умолчанию обёртки нет, `useMemo` добавляют только когда вычисление дорогое (фильтр большого списка), а не на арифметику.
- `useMemo` не бесплатный: хранит прошлый результат и сравнивает зависимости. На дешёвом вычислении он дороже самого вычисления.
- Почитать: https://react.dev/reference/react/useMemo#should-you-add-usememo-everywhere

### Эффект без state: `useDocumentTitle`

- Кастомный хук не обязан содержать state. `useState` нужен, только если значение должно пережить рендер и его смена должна вызвать новый рендер. Здесь значение приходит аргументом и уходит во внешний мир (`document.title`) — state лишний.
- Cleanup восстанавливает прошлый заголовок. На каждом тике: cleanup вернул исходный → новый запуск запомнил исходный → поставил новый. `prevTitle` всегда исходный.
- Cleanup и новый запуск идут подряд в одной задаче — браузер не рисует промежуточное значение, мелькания нет. StrictMode (маунт → анмаунт → маунт) проходит чисто.
- Почитать: https://react.dev/learn/synchronizing-with-effects

## Этап 5

### `useRef` vs `@ViewChild` и поля класса

- `useRef` — коробка `{ current }`, которая живёт между рендерами. Изменение `current` не вызывает ререндер (в отличие от state).
- С атрибутом `ref={audioRef}` React кладёт в `current` сам DOM-элемент — без обёртки `ElementRef`. Аналог `@ViewChild`.
- Начальное значение `null`: при первом рендере элемента ещё нет, React заполняет ref на коммите (как `ngAfterViewInit`) и возвращает `null` при анмаунте. Тип в React 19 — `RefObject<HTMLAudioElement | null>`, перед использованием — narrowing.
- Сам объект ref стабилен (одна коробка на все рендеры) — как `dispatch`, в зависимости эффекта не нужен.
- Не читать и не писать `ref.current` во время рендера — только в обработчиках и эффектах.
- `<audio>` без `controls` не отображается — прятать стилями не нужно.
- Почитать: https://react.dev/learn/referencing-values-with-refs, https://react.dev/learn/manipulating-the-dom-with-refs

### Событие vs эффект: где побочное действие

- Звук — там, где известна причина (интервал закончился, рядом с `dispatch(COMPLETE)`), а не эффектом «`mode` поменялся». `mode` меняют ещё «Пропустить» и табы — такой эффект пищал бы и на них.
- Правило: побочное действие ставится к причине, а не к следствию.
- `play()` возвращает промис, браузер может отказать (autoplay policy) → `.catch(() => {})`, таймер работает и без звука.
- Функция, объявленная на уровне модуля, — не значение компонента, в зависимости эффекта не нужна. Объявленная в компоненте — новая на каждом рендере, линтер потребует её в массив.
- Именованное условие при рендере (`isFinished`) вместо длинного `if` в эффекте: эффект перезапускается только когда оно переключается, а не на каждом тике.
- Почитать: https://react.dev/learn/separating-events-from-effects

### Fast Refresh сохраняет state

- При правке файла Vite подменяет модуль, React сохраняет state компонентов. Lazy init (`createInitialTimerState(DEFAULT_SETTINGS)`) не перезапускается — в `state.settings` старый снимок.
- Поменял дефолты — перезагрузи страницу. В рантайме настройки в таймер попадают только через `APPLY_SETTINGS` (этап 6).

## Этап 6

### `useSyncExternalStore` — подписка на внешний стор

- Для источников, которые меняются вне React (`localStorage`, другая вкладка). Аналог `toSignal(observable)`: React подписывается, а значение отдаёшь синхронно по запросу.
- `subscribe(callback)` — повесить `callback` на изменения, вернуть отписку. Объявлять вне хука: новый `subscribe` на каждом рендере = переподписка.
- `removeEventListener` снимает только ту же функцию, что передали в `addEventListener` (как хранить ссылку на подписку).
- `getSnapshot` — вернуть сырую строку. Не парсить: новый объект на каждый вызов → `Object.is` видит изменение → бесконечный цикл. Строки сравниваются по значению. Может жить внутри хука — React и так вызывает его на каждом рендере.
- Событие `storage` не приходит во вкладку, которая сделала запись → сеттер шлёт `window.dispatchEvent(new Event('storage'))` сам.
- Сеттер пишет в источник правды (`localStorage`), а не в локальную переменную: переменная живёт один рендер, React о ней не знает.
- Updater `prev => next` получает текущее значение из стора, а не из снимка рендера — иначе два вызова подряд дадут +1, а не +2.
- `JSON.parse` бросает синхронно на битой строке → `try/catch`, иначе исключение при рендере = белый экран.
- Почитать: https://react.dev/reference/react/useSyncExternalStore

### Context vs DI

- Ближе всего к DI: провайдер в дереве, потребитель получает ближайшего сверху. Иерархии инжекторов нет — только дерево компонентов.
- В React 19 `<SettingsContext value={...}>` — сам контекст и есть провайдер, `.Provider` не нужен.
- `useSettings` бросает, если контекста нет — ошибка вне провайдера видна сразу.
- При смене `value` перерендериваются все, кто вызвал `useContext`.
- Context живёт в entity, провайдер — в `app` (FSD: фичи не импортируют `app`).
- Почитать: https://react.dev/learn/passing-data-deeply-with-context

### Lazy init — снимок, а не подписка

- `useReducer(reducer, settings, init)` и `useState(() => ...)` читают аргумент один раз на маунте. Новые `settings` из Context таймер не видит — как `this.x = service.value` в конструкторе.
- Сообщить явно: `dispatch(APPLY_SETTINGS)` в обработчике сохранения, рядом с причиной, а не эффектом на `settings`.
- Ограничение MVP: изменения из другой вкладки форма подхватывает, таймер — только после перезагрузки.

### Контролируемая форма vs Reactive Forms

- Нет `FormControl`/`FormGroup`: форма — обычный state. `value` + `onChange` (у чекбокса `checked`). `draft` и есть `form.value`.
- `e.target.value` всегда строка, даже у `type="number"`. Числа в черновике держим строками, чтобы пустое поле было `""`.
- Сабмит обрабатывает форма (`preventDefault`, сбор данных), наружу — доменное событие `onSave(next)` с моделью, как `@Output() save`.
- Типы: `ChangeEvent<HTMLInputElement>`, `SubmitEvent<HTMLFormElement>` (`FormEvent` устарел в `@types/react` 19.3).
- Ошибки валидации — производное значение при рендере, не state.
- Один обработчик на тип поля: имя из атрибута `name`, `{ ...draft, [name]: value }`.

### Сброс state через `key`

- Смена `key` = новый элемент: React размонтирует старый и монтирует новый с чистым state. `key={JSON.stringify(settings)}` пересоздаёт форму ровно когда меняются сохранённые настройки.
- Лучше эффекта с `setDraft`: эффект сначала рисует старый черновик, потом второй рендер.
- Сам объект в ключ нельзя: ключ — строка или число, а объект из `parse` новый на каждом рендере.
- Почитать: https://react.dev/learn/you-might-not-need-an-effect#resetting-all-state-when-a-prop-changes
